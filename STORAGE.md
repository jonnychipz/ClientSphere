# State and storage

ClientSphere supports two storage modes.

## Default production mode

When `AZURE_STORAGE_ACCOUNT` is blank:

- `customer-agents.json` is generated by GitHub Actions, embedded in the private image, and retained as a gzip/base64 Container App environment value for later refreshes.
- The user/admin registry is compressed, encrypted with AES-256-GCM using `SESSION_SECRET`, split across Container App resource tags, and restored on each revision.
- Usage, operational logs, settings, and email action tokens use the single replica's local JSON store.
- The app is fixed at one replica to avoid divergent local stores.

The access/admin registry is durable across deployments. Usage, logs, settings, and action tokens are revision-local and should not be treated as a permanent audit store.

Do not rotate or lose `SESSION_SECRET` without an access-registry reset or migration plan. Existing encrypted tags cannot be decrypted with a replacement value.

## Optional Azure Table Storage mode

Setting `AZURE_STORAGE_ACCOUNT=<account-name>` switches users, usage, logs, tokens, and settings to keyless Azure Table Storage through `DefaultAzureCredential`.

The supplied Bicep intentionally does not create or network a storage account. To enable this mode, separately provide:

1. an Azure Storage account reachable from the Container App;
2. Table service access compatible with your network policy;
3. `Storage Table Data Contributor` for the Container App managed identity;
4. the `AZURE_STORAGE_ACCOUNT` Container App environment value.

The app creates these tables when it starts:

```text
ClientSphereUsers
ClientSphereUsage
ClientSphereLogs
ClientSphereTokens
ClientSphereSettings
```

Do not use an account key or storage connection string. This mode is for deployments that need durable audit/usage history and have designed the required networking and RBAC.
